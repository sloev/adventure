# AGENTS.md — how writers (human and AI) work together in this repo

This repo holds several interactive-fiction books that share one toolchain. Several writers, people and AI agents, work on it at once, often in parallel and often without seeing each other. This file is the contract that keeps us from overwriting each other's work. **Read it before you touch anything.** If something here is unclear, ask before you start, not after you've pushed.

> Claude Code also reads `CLAUDE.md`, which just points here. Other agents: this file is the single source of truth.

---

## 1. What lives where

```
AGENTS.md                      this file (shared, rarely changed)
README.md                      public front page (shared)
docs/FORMAT.md                 the source format (shared, tooling-owned)
tools/  web/                   parser, validator, audit, web + LaTeX renderers (shared, tooling-owned)
books/<slug>/                  one directory per book (book-owned)
  book.md                      metadata + blurb. Its existence makes the book "live" in the build.
  bible.md                     story bible and chapter plan (book-owned, shared by that book's writers)
  canon.md                     the fixed truth of the story world, if the book has secrets (see §5)
  inspiration.md               real-world material the book draws on, and the rules for using it (optional)
  codewords.md                 codeword ledger: the registry of every codeword (see §6)
  FACTCHECK.md                 claims a specialist should verify
  AUDIT.md                     GENERATED by `npm run audit`. Never edit by hand.
  chapters/NN-name.md          one file per chapter, as long as the story needs
  notes/NN.md                  hand-off notes, one per chapter (see §4)
  claims/NN.md                 "I am writing this chapter" markers (see §3)
```

### Length: a target for the whole book, never a unit inside it

Every book aims at **about two weeks of reading for someone who reads it for an hour a day**: roughly 14 hours on an average read-through (≈ 190,000 words on a single path at 230 wpm). That is a *size target for the whole book* and a line for the blurb. It is **not** a structure: no chapter is "one hour", no chapter is a "session", and nothing in the prose, the web reader or the print edition tells the reader how long a chapter takes or that they should stop for the day. Chapters are as long or as short as the story needs; a three-page chapter next to a forty-page one is fine. Use `npm run check` to watch the whole-book total, not per-chapter minutes.

## 2. Branches and merging

- **Never commit to `main` directly.** Everything goes through a branch and a pull request. CI (`.github/workflows/build.yml`) runs `npm run check` and `npm run pdf` on every PR; a red PR is not merged.
- **One branch per unit of work**, named `<writer>/<book>-<what>`, e.g. `claude/next-of-kin-ch03`, `anna/headcount-ch04`, `claude/tools-dna-artifact`. A unit of work is *one chapter*, *one tooling change*, or *one editorial pass*. Not "chapter 4 plus a parser fix".
- **Keep branches short-lived.** Merge `main` into your branch at the start of each working day and before opening the PR (`git fetch origin main && git merge origin/main`). Do not rebase or force-push a branch someone else has pushed to.
- **Never rewrite published history** (`main`, or a branch with an open PR someone else reviews). No `push --force` to shared branches.
- **Never delete or rewrite another writer's passages** on your branch. If you need something changed in a chapter you don't own, see §7.
- Commit messages: `<book> ch<NN>: <what>` (`next-of-kin ch02: the Arkivalieronline evening`), `tools: <what>`, `docs: <what>`. One logical change per commit.

## 3. Claiming work

Two writers drafting the same chapter is the expensive kind of conflict: no merge tool can fix it. So we claim chapters before writing them.

- To claim a chapter, add a new file `books/<slug>/claims/NN.md` on your branch and **push it immediately, before writing anything else**, then open a draft PR. A new file in its own path never merge-conflicts; if a claim file for that chapter already exists on `main` or in an open PR, the chapter is taken: pick another or talk to its owner.
- A claim file is four lines:

  ```
  owner: claude (session https://…) | anna
  branch: claude/next-of-kin-ch03
  started: 2026-11-27
  scope: chapter 3 "Spit" — whole chapter file + notes/03.md
  ```

- Delete the claim file in the PR that finishes the chapter. A claim with no commits for 14 days is stale; anyone may take it after saying so in the PR.
- Tooling changes are claimed the same way, as `tools/claims/<topic>.md`.

## 4. Chapters: the unit of ownership

- **One chapter file = one owner at a time.** Passage IDs carry the chapter-number prefix, which is what makes parallel work safe (Headcount's existing `s4-…` IDs keep their prefix and are never renamed; new books use `c4-…`): IDs are global inside a book, and the prefix guarantees two writers never collide.
- Chapters are linked only through **(a)** the first passage of the next chapter and **(b)** codewords. Do not link into the middle of another writer's chapter. If your chapter must end by jumping somewhere other than the next chapter's start, agree it in the bible first.
- Each chapter is written **after** the previous one exists, or at least its `notes/NN.md`. You may draft ahead from the bible, but you must reconcile with the previous chapter's notes before your PR merges.
- **Hand-off notes** (`books/<slug>/notes/NN.md`) are required with every chapter. They are what the next writer reads instead of the whole chapter:
  - dates, weather, where everyone is at the end;
  - every codeword set, cleared or checked, and on which passage;
  - facts established that later chapters must respect (names, numbers, ages, addresses, what each character now knows);
  - threads opened and not closed;
  - anything you deliberately left for a later chapter to decide.
- **Definition of done** for a chapter PR: `npm run check` clean for *every* book, `npm run audit` clean for your book (commit the regenerated `AUDIT.md`), the book's running total still on course for its whole-book length, every new codeword in the ledger, `notes/NN.md` written, claim file deleted, new factual claims added to `FACTCHECK.md`.

## 5. Shared book files: bible, canon, ledger

These are the files most likely to conflict. Rules:

- **Edit surgically.** Change only the rows or paragraphs you mean to change. Never reflow, reformat, re-sort or "tidy" a shared file in a content PR. A formatting pass is its own PR, announced beforehand, with nothing else in flight.
- **Append, don't rewrite.** New facts go in the chapter's notes file; new codewords as new rows in the ledger; new characters as new bullets in the bible's cast. Prefer adding a line to changing one.
- **`canon.md` is the fixed truth** (what really happened in the past, who is whose child). Prose may only reveal what canon says. Writers may *add* detail that doesn't contradict it. **Changing canon** (contradicting or removing something) is its own PR, touching only `canon.md` (+ the bible if needed), with a list of every chapter it affects. Don't merge a canon change while a chapter that depends on it is claimed, without that chapter owner's agreement.
- The **chapter plan table** in the bible belongs to everyone: change your own row freely; change someone else's row only in agreement with them.

## 6. Codewords

Codewords are the reader's only memory on paper, and every one costs a line on the codeword sheet. They are also the main way chapters written by different people talk to each other.

- **`codewords.md` is the registry.** Reserve a codeword by adding its row (meaning + planned payoff) *before* using it. A name in the ledger is taken, even if no chapter uses it yet.
- Codewords are UPPERCASE, one word, and **never renamed** once merged. Retiring one means `@clear` it where it's spent and mark the row "retired after chNN". Don't reuse a retired name for something else.
- A codeword set in your chapter that a later chapter should check: write the payoff in the ledger *and* in your notes, so the later writer can't miss it.
- Mind the sheet: `npm run audit` reports the most codewords held at once on any route. Stay well under `codeword_sheet` in `book.md`.

## 7. Changing something you don't own

- **Another writer's chapter:** don't edit it on your branch. Open an issue, or comment on their PR, or add a `@note TODO(<owner>): …` line in a *separate* small PR that touches nothing else. Typos and broken links are the exception: fix them in a separate commit titled `<book> chNN: typo fixes`.
- **Another book:** don't touch it at all, except when a tooling change requires it (§8), and then only mechanically.
- **Generated files** (`AUDIT.md`, anything in `dist/`): never hand-merge. On a conflict, take either side and re-run `npm run audit`.

## 8. Shared tooling (`tools/`, `web/`, `docs/FORMAT.md`, `tools/latex/template.tex`)

All books depend on the toolchain, so a change there can break a book you've never read.

- **Tooling changes go in their own branch and PR**, never mixed with chapter prose. Claim them (§3).
- **Additive and backwards-compatible only.** Add a new artifact type, directive or option; do not change the behaviour or syntax of an existing one. If an existing behaviour really must change, the PR migrates every book in the same change and says so in its title.
- A new artifact type lands **complete in one PR**: parser (if needed), web renderer + CSS, LaTeX macro (colour *and* `\gbonebit` variants), `docs/FORMAT.md` entry, and an example in at least one book or fixture. Half-implemented types break the print build.
- **Book-specific styling goes in `books/<slug>/template.tex`**, a copy of the shared template, not in the shared template.
- The PR must pass `npm run check` and `npm run pdf` for **every** book, not just the one you care about.

## 9. Style contracts that apply to every book

- Second person, present tense. One protagonist per book.
- Every real choice has print wording after `|` (see `docs/FORMAT.md`), concrete and non-spoiling.
- Branch and bottleneck: branches rejoin quickly; large consequences surface chapters later via codewords.
- Every passage with choices has at least one unconditional choice. No dead ends (the audit enforces it).
- Real public institutions, websites and tools may appear as props; real private people never; real companies are never shown doing wrong. Invented businesses get invented names.
- No chapter is a timed unit. Never write "session", "about an hour", "a good place to stop" or similar into prose, chapter titles or reader-facing text. The only length target is the whole book's (§1).

## 10. For AI agents specifically

- **Before writing**, read in this order: this file → the book's `bible.md` → `inspiration.md` (if any) → `canon.md` → `codewords.md` → the previous chapter's `notes/NN.md` → the last ~200 lines of the previous chapter (for voice and where everyone is). For tooling work: `docs/FORMAT.md` and the relevant `tools/lib/*.mjs`.
- **Stay inside your claim.** If the task seems to need edits outside the files listed in your claim's `scope`, stop and say so in the PR rather than doing it.
- **Don't invent canon silently.** If the story needs a fact canon doesn't settle (a birth year, who knew what), choose something consistent, and record it in your notes under "Facts established" so it becomes canon for the next writer. If it *contradicts* canon, stop: that's a canon-change PR (§5).
- **Run the checks yourself** before saying a chapter is done. Report the book's running reading-time total and audit result in the PR description, honestly, including warnings.
- **Commit early and push often** to your own branch; cloud containers are ephemeral.
- Keep model names and session internals out of the prose, commit messages and book files.
- **Real people are never material.** Where a book draws on real research (e.g. `next-of-kin/inspiration.md`), borrow its patterns and texture, never a real person's name, dates, photos or story, and never anything about living people or DNA data.
- **Say where you are.** Start your PR description with one status word: `IN PROGRESS`, `BLOCKED` (and on what), `HANDOFF` (what the next writer must do) or `DONE`. Never claim a check passed, a source was read or a link works without having checked it.
